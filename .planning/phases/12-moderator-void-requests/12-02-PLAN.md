<objective>
Build the complete Void Request API surface as one router — the tracer slice that proves the whole workflow end-to-end at the HTTP layer before any UI is written: a moderator creates a request, an admin lists it, approves it, and the underlying sale is voided with an audit record, all against the live `void_requests` table created in Plan 12-01.

Plans 12-03 and 12-04 are pure UI on top of this contract; if the architecture is wrong it must be found here, in one commit, not after two frontend plans have shipped.

Output: `packages/backend/src/routes/voidRequests.ts` with six endpoints; `serializeSale` exported from `sales.ts` so the admin list embeds the identical sale shape the rest of the app already returns; the router mounted in `app.ts`.

existing `errorHandler`): `400 VALIDATION_ERROR` (express-validator array shape, identical to
`sales.ts`), `403 FORBIDDEN`, `404 NOT_FOUND`, `409 DUPLICATE_PENDING_REQUEST`.

Existing symbols this router depends on:
- `prisma`, `PrismaTransactionClient` from `../lib/prisma.js`
- `requireRole` from `../middleware/requireRole.js` — signature `requireRole('admin' | 'moderator')`,
  responds `403 { error: 'FORBIDDEN' }` when `req.session.role` differs
- `serializeSale` from `./sales.js` (this plan adds the `export` keyword to it)
- Session fields available on every request: `req.session.userId`, `req.session.username`,
  `req.session.role`, `req.session.organizationId`

Prisma soft-delete extension caveat (from `packages/backend/src/lib/prisma.ts`): the
`softDeleteFilter` `$extends` injects `status: 'active'` as a default `where` on
`prisma.sale.findMany` and `prisma.sale.findFirst`. Two consequences for this router:
  1. Inside `prisma.$transaction`, `tx` does NOT inherit `$extends` — every sale lookup in a
     transaction must state its `status` explicitly (see the comments already in `sales.ts`).
  2. The extension does not apply to nested relation loads, so `include: { sale: true }` on
     `voidRequest.findMany` returns voided sales too — which is required, since approved
     requests point at voided rows.

New serializer shapes to produce (must match `packages/shared/src/types/voidRequest.ts` from
Plan 12-01 exactly):
  `serializeVoidRequest(vr)` → `{ id, organizationId, saleId, reason, status, requestedById,
   requestedByUsername, reviewedById, reviewedByUsername, reviewedAt, createdAt, updatedAt }`
   with the three date fields as `.toISOString()` or `null`
  `serializeVoidRequestWithSale(vr)` → `{ ...serializeVoidRequest(vr), sale: serializeSale(vr.sale) }`

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Browser → `/api/void-requests` (moderator) | The first moderator-writable endpoint that reaches into another user's potential data. `saleId` is fully attacker-controlled; ownership and status must be re-derived server-side. |
| Browser → `/api/void-requests/:id/approve` and `/reject` (admin) | Two new privileged endpoints that can void a sale row — the same destructive power as the existing `POST /api/sales/:id/void`, so they need the same gate strength. |
| Session store → route handler | `req.session.role`, `userId` and `organizationId` are the sole basis for every authorization decision here; no client-supplied identity is trusted. |
