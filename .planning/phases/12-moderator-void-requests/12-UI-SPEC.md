# Phase 12 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

---

## Design System

| Property | Value |
|----------|-------|
| Tool | none |
| Preset | not applicable |
| Component library | none — hand-rolled Tailwind components (`Modal.tsx`, `StatusBadge.tsx`) + `react-select` v5 (AsyncSelect) + `@tanstack/react-table` v8 |
| Icon library | none — inline hand-drawn SVG icons (`stroke="currentColor"` `strokeWidth="2"`, viewBox `0 0 24 24`, see `AuthenticatedLayout.tsx` sun/moon/hamburger/chevron icons) |
| Font | Tailwind default sans-serif stack — no custom `font-family` declared in `tailwind.config.js` or `index.css` |

**shadcn gate note:** No `components.json` exists (`tailwind.config.js` only, `content: []` — Tailwind classes are applied via `@tailwind` directives with no PurgeCSS content globs, consistent with 11 prior phases). This is Phase 12 of a mature production app with a firmly established hand-rolled Tailwind + Zustand + react-hook-form + react-table design system, documented consistently across every prior UI-SPEC and implementation. Initializing shadcn now would fracture visual consistency rather than serve it, so the gate was not offered — this UI-SPEC extends the existing system exclusively, with every new element modeled directly on an existing component (cited per-section below).

## Spacing Scale

Declared values (must be multiples of 4) — all already established in the codebase, reused as-is for this phase:

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Icon gaps, `|` separators between row actions (`mx-1`) |
| sm | 8px | Compact spacing (`gap-2`, badge vertical padding `py-1`) |
| md | 16px | Default spacing (`px-4 py-2` buttons/cells, `p-4` mobile main content) |
| lg | 24px | Section padding (available, not heavily used pre-Phase-12) |
| xl | 32px | Layout gaps (`md:p-8` desktop main content, empty-state panel `p-8`) |
| 2xl | 48px | Not used in this phase |
| 3xl | 64px | Not used in this phase |

Exceptions: `min-h-[44px]` touch-target minimum on every interactive row action (buttons, nav links) — an established codebase-wide convention, applies to the new Void Request button, Approve/Reject actions, and nav badge row. No new exceptions introduced by this phase.

## Color

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `#ffffff` (white) / `#f9fafb` (`gray-50`) | Table/card/modal surfaces, main content canvas |
| Secondary (30%) | `#f3f4f6` (`gray-100`) / `#e5e7eb` (`gray-200`) | Sidebar/nav background, table header rows, borders |
| Accent (10%) | `#2563eb` (`blue-600`) | Reserved for: the "Submit Request" primary button (reason dialog), active-nav-link left border + text/background, focus rings (`focus:ring-blue-500`) |
| Destructive | `#dc2626` (`red-600`) | Reserved for: the "Void Request" trigger button text, the Approve confirm-dialog primary button (approving executes an irreversible void), the existing Void status badge, the sidebar pending-count notification badge (solid red circle — explicit user-locked exception, see below) |
| Second semantic (Pending) | `#d97706` text / `#fef3c7` bg (Tailwind `yellow-800`/`yellow-100`, `dark:yellow-200`/`dark:yellow-900`) | Reserved for: the new "Pending" status pill only |

Accent reserved for: "Submit Request" button, active nav-link indicator, focus-ring outlines. Never used for the Reject action (see Copywriting/Interaction section — Reject is intentionally neutral gray, matching the existing Deactivate-toggle pattern, not red or blue).

**Locked exception (D-08/D-09, "easy for the admin to notice"):** the sidebar pending-count badge is a solid `bg-red-600 text-white` circle in both light and dark mode (no `dark:` variant swap, unlike every other soft-pastel status pill in this app) — this is a deliberate, user-specified deviation from the softer `bg-red-100/dark:bg-red-900` pill treatment used for the Void status badge, because the badge's job is to be maximally noticeable, not to blend into the sidebar.

## Copywriting Contract

| Element | Copy |
|---------|------|
| Moderator trigger button label | **"Void Request"** (locked by user, D-spec) |
| Trigger button tooltip — eligible row | "Request admin approval to void this row." (native `title` attribute, matches the existing `title=` convention on the disabled Add Row button in `SalesPage.tsx`) |
| Trigger button tooltip — disabled (pending exists) | "A void request for this row is already pending admin review." (D-07: this is the tooltip explaining an already-required disabled state, not a new visual indicator) |
| Reason dialog title | "Void Request" |
| Reason field label | "Reason for Void Request" |
| Reason field placeholder | "Explain why this row should be voided..." |
| Reason field required-validation error | "Reason is required" (inline, matches `ProductModal`'s `errors.name.message` pattern) |
| Reason dialog Cancel button | "Cancel" |
| Reason dialog primary CTA | "Submit Request" (pending label: "Submitting...") |
| Reason dialog submit-failure error | "Failed to submit void request. Please try again." |
| Reason dialog duplicate-pending error (409, D-02) | "A void request for this row is already pending." |
| Admin sidebar nav label | **"Void Requests"** (locked by user) |
| Admin page `<h1>` heading | "Void Requests" |
| Table empty-state heading | "No void requests yet" (bold, matches `AdminSalesTable`'s empty-state heading weight) |
| Table empty-state body | "Void requests submitted by moderators will appear here." |
| Table fetch-error text | "Failed to load void requests. Please refresh the page." (matches `SalesPage.tsx`'s existing `isError` fallback copy verbatim) |
| Status column values | "Pending" / "Approved" / "Rejected" |
| Approve action label | "Approve" |
| Approve confirm dialog title | "Approve Void Request" |
| Approve confirm dialog body | "Approving will void this sale row immediately. This cannot be undone." |
| Approve confirm dialog Cancel button | "Cancel" |
| Approve confirm dialog primary button | "Approve & Void Row" (pending label: "Approving...") |
| Approve failure error | "Failed to approve request. Please try again." |
| Reject action label | "Reject" (instant, no confirm dialog — see Interaction Weight below) |
| Destructive confirmation | Approve: "Approve Void Request" — "Approving will void this sale row immediately. This cannot be undone." (same weight/copy pattern as `VoidConfirmDialog`'s "Void Row" confirm) |

**Interaction weight decision (resolves CONTEXT.md's "Claude's Discretion" item):** Approve gets a confirm dialog styled identically to `VoidConfirmDialog.tsx` (red primary button, disabled Cancel + primary during the round-trip) because it performs the same irreversible void operation. Reject is an instant, no-confirm action styled as a neutral gray text link matching `ProductsPage`'s Deactivate-toggle pattern (`text-gray-600 dark:text-gray-300 hover:text-gray-900`, disables to `text-gray-400 cursor-not-allowed` only for the row being rejected during its round-trip, tracked via a `pendingRejectId`-style local state) — Reject is intentionally the "safe" action visually (gray, not red) because it does not touch sale data and the moderator can resubmit (D-03).

| Approve confirm dialog | new | Direct clone of `VoidConfirmDialog.tsx` (Modal + useMutation + pessimistic Cancel/primary disable) |
| Reject action | new | Instant text-link button styled like `ProductsPage`'s Deactivate toggle (gray, per-row pending disable, no dialog) |

## UI Considerations

> Populated by the ui-phase UI-consideration probe (Step 9.5) and lifted by plan-phase's
> `## UI Considerations` lift rule via the identical rule as SPEC `## Edge Coverage`. Shape-rooted UI *state*
> coverage (empty / loading / error / populated / partial / overflow / zero-one-many / long-text).
> Empty-state and error-state COPY live in `## Copywriting Contract` above — this section covers
> state coverage and REFERENCES those rows rather than restating the copy (de-dup).

Applicable state considerations resolved: 11 covered, 2 backstop, 0 unresolved.

| Category | Element(s) | Status | Resolution / Reason |
|----------|------------|--------|---------------------|
| empty | Reason dialog (form) | ✅ covered | Textarea starts empty every time the dialog opens; Submit is client-side blocked until text is entered — copy row "Reason field required-validation error" above |
| loading | Reason dialog (form) | ✅ covered | All inputs + both footer buttons disabled during the create-request round-trip, matching `VoidConfirmDialog`/`ClockOutConfirmDialog` pessimistic-UI pattern (CLAUDE.md Rule 10) |
| error | Reason dialog (form) | ✅ covered | Submit-failure and 409-duplicate-pending errors render inline below the form — copy rows "Reason dialog submit-failure error" / "duplicate-pending error" above |
| empty | Void Requests table (list-collection) | ✅ covered | Zero-requests-ever state renders the `AdminSalesTable`-style empty panel — copy rows "Table empty-state heading/body" above |
| loading | Void Requests table (list-collection) | ✅ covered | Initial fetch shows the existing bare-text loading convention (`Loading void requests...`, matching `AdminSalesTable`'s `Loading sales...`) |
| error | Void Requests table (list-collection) | ✅ covered | Fetch failure text — copy row "Table fetch-error text" above, reuses `SalesPage.tsx`'s exact existing `isError` fallback pattern |
| populated | Void Requests table (list-collection) | ✅ covered | Rows mirror `AdminSalesTable` exactly (same 8 base columns + Reason + Status, newest-first, white/red-void striping) — Component Inventory row above |
| overflow / long-text | Void Requests table — Reason column (list-collection / static-content) | ✅ covered | Long Reason text truncates via `line-clamp-2` with full text on native `title`-attribute hover — identical to the existing Notes column treatment (D-05 explicit requirement) |
| zero-one-many | Void Requests table (list-collection) | ✅ covered | Zero → empty-state panel; one or many → renders newest-first through the existing `PaginationFooter`, no special-casing at any row count (matches `AdminSalesTable`) |
| loading | Approve confirm dialog (interactive-control) | ✅ covered | Cancel + primary button both disabled during the approve round-trip, primary label switches to "Approving..." — matches `VoidConfirmDialog` exactly |
| error | Approve confirm dialog (interactive-control) | ✅ covered | Failure renders inline in the dialog — copy row "Approve failure error" above, identical placement/style to `VoidConfirmDialog`'s error paragraph |
| loading | Reject action (interactive-control) | ✅ covered | Reject button grays out (`text-gray-400 cursor-not-allowed`) only for the row being rejected during its round-trip — identical per-row pending pattern to `ProductsPage`'s Deactivate toggle, no confirm dialog (see Interaction Weight decision) |
| error | Reject action (interactive-control) | 🧪 backstop | No dedicated error UI is specified for a failed Reject call — `ProductsPage`'s Deactivate toggle has no visible error affordance either (silent retry-on-click is the only existing precedent in this codebase); planner/executor should confirm this silent-failure precedent is acceptable for Reject, or add a minimal inline error, since a silently failing Reject could read as a no-op to the admin |
| loading | Sidebar pending-count badge (nav) | ✅ covered | Badge is omitted entirely (not rendered as "0", no spinner/placeholder) until the pending-count query resolves — avoids a flash of an incorrect count, extends D-09's "hidden at 0" rule to "hidden until loaded" |
| error | Sidebar pending-count badge (nav) | 🧪 backstop | If the pending-count query fails, the badge should fail silently (omitted, same visual as zero/loading) rather than show a stale or error count — there is no existing nav-badge in this codebase to confirm this fallback against (it is the first notification badge introduced); planner/executor should verify this is the intended behavior at implementation time |
| overflow | Sidebar pending-count badge (nav) | ✅ covered | Count is capped for display at 99; values over 99 render "99+" inside the same fixed pill shape — new design decision, no prior notification-badge precedent exists in this codebase to inherit from |
