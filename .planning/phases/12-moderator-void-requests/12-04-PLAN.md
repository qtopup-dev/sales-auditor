<objective>
Build the admin-facing half of the Void Request workflow: a new admin-only `/void-requests` page with a sales-shaped review table, an Approve confirm dialog that triggers the transactional void, an instant Reject action, and the red pending-count badge on the sidebar nav entry.

Purpose: this is where the admin actually adjudicates requests, and where PHASE12-SC2, SC3, SC4 and SC5 become observable. Every visual and copy decision is already locked in `12-UI-SPEC.md`; this plan implements it against the API contract Plan 12-02 delivered.

Output: `VoidRequestsTable.tsx`, `ApproveVoidRequestDialog.tsx`, `VoidRequestsPage.tsx`, the `/void-requests` route, and the `ADMIN_NAV` entry with its badge.
</objective>

<!-- API contract delivered by Plan 12-02 (see 12-02-SUMMARY.md for as-built detail) -->

GET   /api/void-requests                 (admin) → 200 `VoidRequestWithSale[]`, newest-first
GET   /api/void-requests/pending-count   (admin) → 200 `{ count: number }`
PATCH /api/void-requests/:id/approve     (admin) body `{}` → 200 `VoidRequestWithSale`
PATCH /api/void-requests/:id/reject      (admin) body `{}` → 200 `VoidRequestWithSale`

Both PATCH calls MUST send an explicit empty object body — `api.patch(url, {})`. This deploy
chain's outer proxy mishandles bodyless PATCH/POST requests; `ProductsPage.tsx`'s toggle
mutation carries the same `{}` and the same explanatory comment.

Shared types (Plan 12-01):
`import type { VoidRequestWithSale, VoidRequestStatus } from '@alejinput/shared';`
`VoidRequestWithSale` = the request fields (`id`, `saleId`, `reason`, `status`,
`requestedByUsername`, `reviewedByUsername`, `reviewedAt`, `createdAt`, ...) plus
`sale: Sale`, so every sales column reads off `row.original.sale.*` and the Reason/Status
columns read off `row.original.*`.

React Query keys used by this plan:
  `['void-requests']`                    — the admin list
  `['void-requests-pending-count']`      — the sidebar badge
  `['void-request-pending-sale-ids']`    — owned by Plan 12-03; approve/reject must invalidate
                                            it too so the moderator's button state recovers
  `['sales']`, `['admin-summary']`       — pre-existing; approve voids a row so both go stale

Status pill palettes (UI-SPEC Color table; the Approved and Rejected palettes are reused from
existing badges rather than invented):
  Pending  — `bg-yellow-100 text-yellow-800 dark:bg-yellow-900 dark:text-yellow-200`
  Approved — the existing Active-badge palette in `AdminSalesTable.tsx`'s Status column
  Rejected — the existing inactive/neutral gray badge palette used by `StatusBadge.tsx`
All three use the shared pill shell `inline-flex items-center px-3 py-1 rounded-full text-xs font-normal`.

Sidebar badge markup (UI-SPEC Component Inventory, verbatim class string):
`min-w-[20px] h-5 px-1 rounded-full bg-red-600 text-white text-xs font-semibold leading-none
flex items-center justify-center` — deliberately solid red in both themes with no `dark:`
variant, unlike every other pill in this app, because its job is to be maximally noticeable.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Browser → `/void-requests` route | A client-side route guard decides what renders; it is not what protects the data. The endpoints behind the page carry their own gates. |
| Admin browser → approve/reject endpoints | The only UI path to voiding a sale row through this feature. The dialog's confirm step is a mistake guard, not a security control. |
| Reason text (moderator-authored) → admin DOM | The first place another user's free-text input is rendered into an admin's page in this phase. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-12-21 | Elevation of Privilege | `/void-requests` route reachable by a moderator | high | mitigate | The route is nested under the existing `<ProtectedRoute requiredRole="admin" />`, which redirects non-admins to `/sales`; independently, `GET /api/void-requests`, `/pending-count`, `/approve` and `/reject` all carry `requireRole('admin')` server-side, so a moderator who forces the route sees an empty, erroring page and can mutate nothing (CLAUDE.md Rule 9). |
| T-12-22 | Tampering (XSS) | Moderator-authored `reason` rendered in the admin table | medium | mitigate | The Reason cell renders through JSX text interpolation and a `title` attribute, both auto-escaped by React. No `dangerouslySetInnerHTML` is introduced. This mirrors how the existing Notes column already renders moderator-authored text. |
| T-12-23 | Tampering | Accidental irreversible void via a mis-click | medium | mitigate | Approve requires a confirm dialog whose copy states the void is immediate and cannot be undone, and whose buttons are disabled for the duration of the round-trip. Reject, which is recoverable, is deliberately instant and neutral-gray so the two are not visually confusable. |
| T-12-24 | Repudiation | An approve that voids a row without a visible trail | high | mitigate | The server writes the `void` AuditLog entry inside the approve transaction (Plan 12-02, CLAUDE.md Rule 2), and the request row itself retains `reviewedById` / `reviewedByUsername` / `reviewedAt` and stays visible in this table forever (D-04) — the review decision is doubly recorded. |
| T-12-25 | Information Disclosure | The pending-count endpoint queried by a moderator session | medium | mitigate | The query is gated with `enabled: user?.role === 'admin'` on the client and `requireRole('admin')` on the server; a moderator session issues no request and would receive 403 if it did. |
| T-12-26 | Denial of Service | Rapid repeated Approve or Reject clicks | low | accept | Per-row pending state disables the buttons during each round-trip, and the server's `status: 'pending'` guard turns any extra call into a 404 rather than a duplicate mutation. No rate limiter exists in this app today and Phase 12 does not add the first one. |
| T-12-27 | Information Disclosure | Cross-organization requests appearing in the table | high | mitigate | Every void-request query on the server is scoped to `req.session.organizationId` (Plan 12-02); the client sends no organization parameter and cannot widen the scope. |
| T-12-SC | Tampering | npm/pip/cargo installs | high | mitigate | This plan installs no packages — `@tanstack/react-table`, `@tanstack/react-query` and `axios` are all already in `packages/frontend/package.json`. No package-legitimacy checkpoint is required. |
